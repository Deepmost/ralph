# Task Decomposition for Ralph

将需求文档和设计文档拆分为一组可直接交给 Ralph 循环脚本执行的任务文件，保存到当前项目根路径下 `scripts/ralph/tasks/` 目录。

这个 skill 的职责只有一个：**把文档拆成可执行任务。不要直接开始开发，不要跳过拆分阶段。**

---

## 适用场景

当用户提供以下任意材料时使用：

- 需求文档 / PRD
- 技术设计文档 / 方案设计
- 页面原型、接口说明、数据库设计补充
- 一段描述完整需求和实现方案的长文本

目标是产出一组：

- 粒度合适
- 依赖明确
- 具备具体技术落点
- 能被 Ralph 一次一任务顺序执行

的开发任务。

---

## 输入原则

优先同时读取“需求文档”和“设计文档”。

- **需求文档**决定做什么、为什么做、用户行为和业务边界
- **设计文档**决定怎么做、改哪些模块、数据结构和接口方案

如果两者都存在：

1. 先用需求文档界定范围和验收目标
2. 再用设计文档确定拆分边界和技术实现路径

如果存在冲突：

- 业务行为冲突：不要擅自决定，先指出冲突并请求澄清
- 纯实现细节冲突：可优先采用更新、更具体、风险更低的设计方案，但必须在任务描述里写清假设

如果只有需求没有设计：

- 仍可拆分任务，但必须显式写出假设和待确认点
- 避免生成过度依赖未定技术选型的大任务

---

## 工作流程

1. 阅读用户提供的需求文档、设计文档及补充材料
2. 提取用户目标、核心业务流程、边界条件和非功能要求
3. 识别技术实施路径：数据层、接口层、服务层、页面/组件层、集成层、测试/验证层
4. 将需求按依赖关系拆分为多个可独立完成的实现任务
5. 为每个任务补全可执行的技术设计、约束和验收标准
6. 按执行顺序写入 `scripts/ralph/tasks/` 目录中的独立 MD 文件

---

## 输出格式

每个任务生成一个独立的 MD 文件，使用 YAML frontmatter 存储元数据。

**文件命名**: `{序号}-{简短英文描述}.md`，例如 `001-add-status-field.md`

```markdown
---
id: "001"
title: "任务标题"
priority: 1
depends_on: []
branch: "ralph/feature-name"
---

# 任务标题

## 背景上下文
（业务背景、所属模块、上游/下游任务关系、必要假设）

## 需求描述
（精确描述本任务要交付什么，包括输入输出、状态变化、交互行为、边界条件）

## 技术设计
（需要新增/修改的文件、接口定义、数据模型、迁移方案、核心逻辑、集成点）

## 实现约束
（必须遵循的基础设施、框架约定、目录约定、兼容性要求、禁止事项）

## 验收标准
（Ralph 可以实际检查的结果、命令、验证步骤和预期输出）
```

## 第一规则：任务必须足够小

**每个任务都必须能在一次 Ralph 迭代中完成。**

Ralph 每次迭代都会启动一个新的 pi agent 实例。任务太大时，单次迭代无法稳定完成，后续任务也会因为上下文丢失而出现返工或破坏。

### 合适的任务

- 添加一个数据库字段和 migration
- 为现有 API 增加一个明确的查询参数
- 新增一个可复用组件并接入现有页面
- 为某个表单补齐提交逻辑和校验
- 为已存在的数据流增加状态映射或错误处理

### 太大的任务

- “完成整个后台管理页面”
- “实现整套认证系统”
- “把整个订单模块重构掉”
- “实现这个 PRD 的全部内容”

### 拆分经验法则

核心判断标准：**任务能否在一次 Ralph 迭代中稳定完成。**

以下信号提示任务可能过大：

- 如果一个任务涉及多个独立业务实体的跨层改动（单个实体的 schema → service → API → UI 全链路是正常的）
- 如果一个任务需要修改多个不相邻模块
- 如果一个任务的验收标准需要依赖多个未完成子步骤，应该继续拆分
- 如果一个任务包含多个可独立交付的功能点，应该拆开

---

## 拆分策略

优先按“真实开发顺序”拆分，而不是按文档章节机械拆分。

常见顺序如下：

1. 基础准备：配置、依赖、feature flag、类型定义、常量
2. 数据层：schema、migration、ORM model、repository
3. 接口与服务层：API contract、server action、service、权限校验
4. 页面与组件层：表单、列表、详情、状态组件、交互逻辑
5. 集成层：把前后端串起来，补齐状态同步、错误处理、埋点
6. 验证与收尾：测试、回归检查、文档更新、监控补充

当某个功能较大时，优先用这些边界继续切：

- 按数据模型拆分
- 按 API/endpoint 拆分
- 按页面或组件职责拆分
- 按用户流程步骤拆分
- 按集成顺序拆分

不要这样拆：

- “前端部分”
- “后端部分”
- “优化代码”
- “联调一下”

这类任务过于模糊，Ralph 无法稳定执行。

---

## 任务内容必须具体

每个任务都必须尽量写清楚以下信息：

- 需要新增或修改的具体文件路径
- 涉及的数据模型、字段、接口或组件名
- 关键逻辑步骤
- 与哪些前置任务有关
- 本任务不应该做什么
- 如何验证完成

### 技术设计必须落地

技术设计不能只写“实现接口”或“完成页面”。至少要说明：

- 修改哪些目录或文件
- 新增什么类型、schema、接口、组件或测试
- 数据如何流转
- 与现有模块如何集成

### 验收标准必须可验证

验收标准不能写成“功能正常”“代码整洁”“页面好看”。要写成 Ralph 能检查的事实。

好的例子：

- `users` 表新增 `last_login_at` 列，允许为空
- `/api/projects` 支持 `status` 查询参数并返回过滤结果
- 提交表单后出现成功提示，列表中显示新创建记录
- `pnpm typecheck` 通过
- `pnpm test --filter project-service` 通过
- 使用 `agent-browser` 在浏览器中验证新增 UI 流程

## 编号与依赖规则

1. **每个任务一个 MD 文件**
2. **文件名序号固定三位数**：`001`、`002`、`003`
3. **编号顺序必须与执行顺序一致**
4. **较早任务不能依赖较晚任务**
5. **priority** 按依赖顺序排序；同层任务按业务优先级和实现顺序排序
6. **depends_on** 只写直接前置任务，不要写所有祖先任务
7. **branch** 从功能名派生，使用 kebab-case，前缀为 `ralph/`
8. **一次需求拆分的所有任务必须使用同一个 branch**。禁止按阶段、模块或 phase 创建多个分支。一个需求 = 一个分支，所有任务在该分支上顺序开发

---

## 文档拆分判断规则

当用户同时给了需求文档和设计文档时，不要简单按文档数量产出任务。应先做统一抽象：

1. 识别用户故事 / 核心用例
2. 将每个用例映射到实现层
3. 找出前置依赖
4. 合并重复实现点
5. 输出最小可执行任务集

### 示例

原始需求：

> “新增项目成员邀请功能，支持邮箱邀请、角色选择、接受邀请、过期处理。”

设计文档给出：

- `project_invitations` 表
- `POST /api/projects/:id/invitations`
- 邀请邮件模板
- 邀请接受页面

合理拆分：

1. `001-project-invitation-schema.md`
2. `002-project-invitation-create-api.md`
3. `003-project-invitation-email-template.md`
4. `004-project-invitation-accept-flow.md`
5. `005-project-invitation-expiry-and-validation.md`

而不是产出一个“大一统邀请功能”任务。

## 归档之前的运行

在生成新任务文件之前，检查是否存在来自之前运行的文件：

1. 检查 `scripts/ralph/tasks/done/` 是否已有已完成任务
2. 如果有，创建归档目录：`archive/YYYY-MM-DD-tasks/`
3. 将 `done/` 下的任务文件和 `scripts/ralph/progress.txt` 复制到归档目录
4. 清空 `done/` 目录，并重置 `progress.txt`
5. 再生成新的任务文件

---

## 生成时的强制要求

- 只生成“开发任务”，不要生成“继续思考”“阅读代码”“人工确认一下”之类的空任务
- 不要把多个独立目标塞进同一个任务
- 不要产出缺少技术落点的任务
- 不要产出无法验收的任务
- 不要让任务依赖未来编号的文件
- 不要在没有依据时编造不存在的目录结构；不确定时写“或对应模块文件”，但仍要尽量具体

---

## 保存前检查清单

在生成任务文件之前，确认：

- [ ] 已基于需求文档和设计文档完成统一拆分，而不是照抄原文结构
- [ ] 之前的运行已归档
- [ ] 每个任务都能在一次 Ralph 迭代中完成
- [ ] 任务已按依赖顺序编号
- [ ] 每个任务都包含足够具体的技术设计
- [ ] 每个任务都包含可验证的验收标准
- [ ] 每个任务都有 `Typecheck passes` 或等价的类型检查标准
- [ ] 有测试价值的任务包含测试验证要求
- [ ] UI 任务包含 `Verify in browser using agent-browser`
- [ ] 所有任务使用同一个 branch（禁止按阶段/模块拆分多个分支）
