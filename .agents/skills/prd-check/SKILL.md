# PRD 需求文档审核

以资深需求分析师的视角，对一份 PRD 进行系统化审核，找出歧义、遗漏、矛盾与不可执行项，并产出一份可直接用于评审会的结构化报告。

## 审核目标

一份合格的 PRD 必须能回答 6 个核心问题（缺一即为重大缺陷）：

1. **为什么做** — 背景、痛点、目标是否清晰且可衡量
2. **给谁用** — 用户角色与使用场景是否明确
3. **做什么** — 功能范围、边界是否界定（含「不做什么」）
4. **怎么用** — 流程、交互、字段规则是否完整
5. **有哪些规则和边界** — 业务规则、异常、权限是否覆盖
6. **做到什么程度算完成** — 验收标准是否可量化、可测试

## 审核流程

1. **定位文档**：确认待审 PRD 路径；若未提供，询问或在工作目录中查找 `*.md` / `*.docx` 等需求文档。
2. **通读全文**：用 Read 完整读取，建立整体认知，不要只看局部。
3. **逐维度检查**：按下方「六大审核维度」逐项核对，参考 `checklist.md` 的细则。
4. **标注问题**：每个问题标注严重级别（见「问题分级」）、所在章节、具体描述、修改建议。
5. **产出报告**：按「输出格式」生成审核报告。
6. **给出结论**：明确给出「可进入研发 / 需修改后复审 / 打回重写」的判定。

## 六大审核维度

> 详细检查项见同目录 `checklist.md`，审核时必须逐条比对。

- **完整性**：对照模板 19 个章节，缺失或留空的关键章节即为问题。
- **清晰性**：描述是否无歧义、无「等」「类似」「大概」等模糊词；流程是否有明确触发条件与结果。
- **一致性**：章节间是否自洽（如功能需求 vs 字段规则 vs 接口；状态流转 vs 异常流程）。
- **可执行性**：研发/测试能否仅凭文档实现，无需反复追问；校验规则、保存逻辑是否明确。
- **边界与异常**：异常流程、边界值、空/错/超时/无权限场景是否覆盖。
- **可验收性**：验收标准是否可量化、可测试，是否与功能需求一一对应。

## 问题分级

- **P0 阻断**：缺失会导致无法开发或方向性错误（如无目标、无核心流程、范围不清）。
- **P1 严重**：会导致返工或线上风险（如异常未覆盖、规则矛盾、验收不可测）。
- **P2 一般**：影响质量但可并行补充（如埋点缺失、文案不统一、措辞模糊）。
- **P3 建议**：优化项（如可读性、排版、补充示例）。

## 输出格式

````markdown
# PRD 审核报告

| 项目 | 内容 |
| --- | --- |
| 文档名称 | xxx |
| 审核时间 | YYYY-MM-DD |
| 审核结论 | ✅ 可进入研发 / ⚠️ 需修改后复审 / ❌ 打回重写 |
| 问题统计 | P0: x  P1: x  P2: x  P3: x |

## 一、核心问题（6 问自检）
逐条给出「为什么做/给谁用/做什么/怎么用/规则边界/完成标准」是否满足。

## 二、问题清单

| 级别 | 章节 | 问题描述 | 修改建议 |
| --- | --- | --- | --- |
| P0 | 2.3 需求目标 | 目标无量化指标，无法衡量是否达成 | 补充如「客服工单量下降 30%」 |

## 三、亮点（可选）
值得肯定的部分，便于团队复用。

## 四、复审重点
若结论为「需修改后复审」，列出复审时必须重点核对的项。
````

## 注意事项

- 只审核、不擅自修改原文档；如用户要求修改，再单独执行。
- 基于文档事实评判，不臆测；无法判断的项明确列为「待确认」。
- 区分「文档缺陷」与「需求本身的业务风险」，后者归入风险提示而非格式问题。
- 审核语言与原文档保持一致。
